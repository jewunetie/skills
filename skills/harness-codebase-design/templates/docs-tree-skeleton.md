# Docs tree skeleton

A starter structure for the `docs/` system of record. Adapt to the project. Not all directories are needed on day one. Add them when they earn their place.

## Top-level layout

```text
AGENTS.md                     # ~100 lines, table of contents (see AGENTS.md template)
ARCHITECTURE.md               # top-level map of domains and package layering
docs/
  design-docs/
    index.md                  # catalog with verification status per doc
    core-beliefs.md           # agent-first operating principles
    [topic].md                # one design doc per topic
  exec-plans/
    active/                   # in-flight execution plans
    completed/                # archived plans
    tech-debt-tracker.md      # known debt, versioned
  product-specs/
    index.md
    [feature].md
  generated/                  # auto-generated, do not hand-edit
    db-schema.md              # auto-regenerated from schema
  references/                 # vendored LLM-readable docs for external deps
    [framework]-llms.txt
  QUALITY_SCORE.md            # graded quality per domain or layer
  PRODUCT_SENSE.md            # product principles the agent applies
  GLOSSARY.md                 # domain terms for the agent's reference
```

## What goes in each directory

### `docs/design-docs/`

One file per architectural decision, design discussion, or conceptual document the agent might need.

`index.md` is the catalog. Format:

```markdown
| Doc | Status | Last verified | Owner |
|---|---|---|---|
| auth-architecture.md | verified | 2026-04-01 | @alice |
| caching-strategy.md | stale | 2025-11-15 | @bob |
| event-bus-design.md | active | 2026-04-22 | @carol |
```

Verification status matters. The doc-gardening agent (if you run one) updates this column when it scans for staleness.

`core-beliefs.md` captures the agent-first principles for this codebase. Examples of the shape:

```markdown
- We prefer boring, well-trained-on technologies over novel ones.
- We validate at boundaries, never trust input shape.
- We centralize cross-cutting concerns through Providers.
- We accept agent-style verbosity over human-style cleverness when correctness is at stake.
```

### `docs/exec-plans/`

Plans for non-trivial work. Lightweight ephemeral plans for small changes can live in chat or in feature branches. Anything spanning multiple sessions or engineers belongs here.

`active/` contains in-flight plans. Each plan is a markdown file with:

- Goal (one paragraph).
- Acceptance criteria (testable).
- Decomposed steps.
- Decision log (what was chosen, what was rejected, why).
- Progress (updated as work proceeds).

`completed/` is the archive. Old plans get moved here so the agent does not waste tokens reading them.

`tech-debt-tracker.md` is a versioned list of known debt. Each entry has scope, age, blast radius, and (if known) a proposed approach.

### `docs/product-specs/`

Specifications for features, written before or alongside implementation. The planner agent (if you run a planner/generator/evaluator harness) writes these from short user prompts.

`index.md` is a catalog. Each spec has scope, user stories, success criteria, and (if helpful) technical architecture guidance at a high level. Avoid granular technical specifics; they propagate downstream errors.

### `docs/generated/`

Auto-generated documentation. The agent should never hand-edit these. Each file should have a header noting:

```markdown
> This file is generated by `[script-or-command]`. Do not edit manually.
> Regenerated: 2026-05-01
```

Common contents: database schema, API surface, type definitions exported from the project.

### `docs/references/`

Vendored, LLM-readable documentation for external dependencies. One file per major dependency:

```text
docs/references/
  react-llms.txt
  fastapi-llms.txt
  postgres-llms.txt
  internal-design-system-llms.txt
```

The naming convention `[name]-llms.txt` matches the emerging community standard. Many projects publish official `llms.txt` files; for those that do not, generate one with an agent and check it in.

This is faster than the agent fetching docs at runtime and pinnable to a known version.

### `docs/QUALITY_SCORE.md`

A grade per domain or architectural layer. Updated by a scheduled cleanup agent (or manually for smaller projects).

Sample format:

```markdown
# Quality scores

Last updated: 2026-05-01

| Domain | Grade | Trend | Notes |
|---|---|---|---|
| auth | A | steady | All invariants enforced. Three minor TODOs. |
| billing | B+ | improving | Two functions over size limit; one stale doc. |
| analytics | C | degrading | Layer violations in 4 files. Logger inconsistency. |
| migrations | A- | steady | Manual review required for new migrations. |
```

The grade itself is back-pressure. A degrading grade triggers attention.

### `docs/PRODUCT_SENSE.md`

Product principles the agent applies when making design decisions. Examples of the shape:

```markdown
- Prefer simple over clever in user-facing copy.
- Default to opt-out for safe-by-default features.
- Errors should be specific and actionable.
- Loading states matter; never show a blank screen.
```

This is the closest the agent gets to human judgment about product. Keep it short.

### `docs/GLOSSARY.md`

Domain terms in the project's specific meaning. When the agent encounters a term, this is the first place it looks.

```markdown
- **Account**: a paying customer entity. NOT a user.
- **User**: an individual person, possibly belonging to an Account.
- **Workspace**: an isolated environment within an Account.
- **Invitation**: a pending offer for a User to join a Workspace.
```

Useful when the project's domain vocabulary differs from common usage.

## Stub `init.sh` for the project root

```bash
#!/usr/bin/env bash
set -euo pipefail

# Boots the project for a single agent worktree.
# This script should be idempotent: running it twice should not break anything.

# 1. Install dependencies if needed
if [ ! -d node_modules ]; then
  npm install
fi

# 2. Start backing services in the background (database, cache, queue)
docker compose up -d --quiet-pull

# 3. Run database migrations
npm run db:migrate

# 4. Start the dev server
npm run dev &
DEV_PID=$!

# 5. Wait for it to be ready
until curl -s http://localhost:3000/health > /dev/null; do
  sleep 1
done

echo "App ready at http://localhost:3000 (pid $DEV_PID)"
```

Replace with project-specific commands. The pattern: a single command boots everything, idempotently, in under a minute.

## Stub `progress.md` for long-running work

```markdown
# Progress log

## 2026-05-01

Worked on the auth domain. Implemented invitation acceptance flow.
- Added `POST /invitations/:id/accept` endpoint.
- Added `Invitation.accept()` service method.
- Added Playwright test covering the happy path.

Next: handle the case where the invited email is already a User. Currently returns 500.
```

Each session appends. The agent reads the most recent few entries on session start.
